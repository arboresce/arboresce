# Isolated migration and transaction expectations

These independently reviewed literals precede the application/PostgreSQL
consumer. They qualify a synthetic harness, not a product database, tenant
authorization, bootstrap, lifecycle continuity, idempotent commands or recovery.
The governing owners are storage-and-search, deployment, resource-profiles,
dependency-qualification and testing-and-coverage.

The useful typed record contains an organization identifier, a record identifier,
a content revision and a Gregorian date. All are already checked domain values.
The database preserves their exact values, including revisions above binary64's
exact-integer range. The immutable record key is organization plus record ID.
Duplicate keys cannot replace accepted data. No application port exposes SQLx,
database connections, credentials or transport types.

`cases.json` owns the complete record literals and scenario expectations. Scenario
steps use those records by name; final rows are independently enumerated record
names, not results generated by the adapter. Every scenario starts with a fresh
owned database unless its steps explicitly test upgrade/reconnect/replay. Parallel
checks have distinct namespaces. Schema versions are positive ordered integers.
Version 1 creates the typed record relation. Version 2 adds a default-empty
annotation of at most 256 UTF-8 bytes, preserving Unicode without normalization
and rejecting U+0000 as PostgreSQL text requires. This changes none of the original
columns or their meaning. Old readers
and writers continue to operate after expansion. Schema downgrade is unsupported;
an older migration set must reject the newer database without changing it. Failed
transactional DDL leaves neither the new relation nor an applied-version receipt.
Checksums and missing versions are never ignored to make a run pass. Applied
receipts must be an exact successful prefix of the ordered selected set. A gap
inside that history is rejected before any DDL, write, replay or repair. The
administrative gap fixture removes only version 1's receipt after a complete
version-2 migration; exact useful row/annotation/schema remain unchanged and the
final history remains `[2]`. This integrity behavior belongs to the adapter;
it is not inferred from SQLx's version/checksum validation.

Direct constraint cases start at schema version 2 with an empty relation and the
fully valid `exact-large` record plus empty annotation. Override exactly the
declared SQL column with its literal SQL value; every other field remains valid.
Each rejected insert leaves zero rows. This setup makes the stated SQLSTATE a
discriminator for the intended constraint. Annotation boundary cases independently
enumerate text recipes, exact UTF-8 byte lengths and successful unchanged readback.

Committed means an actual positive COMMIT completion was received. A statement
failure is NotCommitted only after a positive ROLLBACK completion. Failure before
any write can be NotCommitted/Unavailable. A lost COMMIT or ROLLBACK completion is
Unknown and triggers no automatic write retry. Cancelling or dropping a pending
call supplies no positive result. The same uncertainty rule applies even where an
independent observation later proves that the server did commit or roll back.
These are transaction boundaries, not an idempotency ledger or a recovery claim.

The commit-loss and rollback-loss cases use a measured, bounded local protocol
relay. It forwards actual PostgreSQL traffic and withholds the matching server
CommandComplete frame before closing its owned streams. An independent direct
connection checks the exact final rows. No mock transaction result supplies the
uncertainty evidence. Migration concurrency uses actual database lock-wait
observations and an explicit release barrier; sleeps alone do not prove overlap.

The selected local resource input is PostgreSQL 17.11 on native macOS ARM64,
direct protected Unix sockets, a task-owned fresh cluster/database and separate
synthetic migration and non-owner writer roles. The public runtime still cannot
provision an owner or write product state. PostgreSQL/pooler RLS, lifecycle,
packaged restoration, Linux service/native-release and managed capacity retain
their own gates. Exact preparation, server identity/configuration, limits, role
checks and bounded owned shutdown must pass before this profile is consumed.
Installed clients and a handwritten readiness record are insufficient.

The native collector's service input is explicit and separately hash-bound.
Absent input fails required service tests; it never silently skips them. Ambient
service variables cannot select a target. A public-only standalone run receives
its own freshly prepared isolated service input and the same frozen literals.
Every maintained reader, relay and observation helper is measured source; assertion
bodies are excluded from coverage numerators. Existing pure fixtures, caps,
deadlines, required cases and supported-profile qualifications remain unchanged.

All material is self-authored synthetic data. It contains no personal evidence,
private service reference or operational credential.
