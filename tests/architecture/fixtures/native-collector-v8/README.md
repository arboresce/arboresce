# Optional service collection protocol

These original synthetic fixtures extend the actual finite three-package Cargo
and LLVM collector experiment. The stable case adds an explicitly selected,
filesystem-only service descriptor to the existing successful experiment. Its
original result, suite, profile and scope expectations remain required. Other
existing experiments continue to exercise collection without a service selector.

The descriptor binds six exact files, separate tool identities, a literal
readiness record and task-owned canonical data and socket directories with mode
0700. Its lease is bounded to 180 seconds from preparation. The tool files are
literal text and are never executed. This experiment qualifies collector input
and selection behavior; actual PostgreSQL readiness, native service collection,
migrations and restart require their separate real-service qualification.

The required miniature test must obtain the explicit selector and independently
read the bound configuration before writing the exact selected input path to an
owned witness. A missing selector or changed initial payload fails that test.
The stable case requires exact before/after service identity and physical file
conservation, both tool hashes in frozen inputs, no synthetic-tool launches, and
complete ordinary native receipt/profile qualification.

The negative case changes only the bound configuration during actual required
test execution, after asserting its original exact bytes. All source, descriptor,
tool, readiness and other bound file bytes remain unchanged. The miniature suite
must complete successfully and its output must contain the literal mutation
witness. Final service reobservation must then reject changed input, retain the
failed output and final prepared identity, and produce neither final source
identity nor a success result. A preparation error or earlier test failure does
not satisfy this expectation.

Keep all earlier cases and source roles. These additions do not change coverage
thresholds, process/profile conservation, output caps or operation deadlines.

The selected-executable literals separately check the collector's ordered lookup
of registered objects, prepared tools and optional service tools. A selected hash
must resolve to the exact recorded executable path. Unknown hashes, changed paths,
using one tool's hash for another path, and an absent service cannot authorize a
launch. An object with the same hash retains lookup precedence; a mismatched
registered path cannot fall through to a service path. These supplied records
qualify resolver semantics, not an actual native launch or PostgreSQL behavior.
The two closed-output cases require failure when the service help cannot write
stdout or the wrong-arity diagnostic cannot write stderr.
