# Two explicitly prepared PostgreSQL cohorts

These original synthetic fixtures are provided under MIT OR Apache-2.0. They
define a finite allocation of two independently prepared services for one complete
unfiltered native collection. Inert descriptor, configuration and tool bytes
qualify only protocol intake; they establish no live database or recovery result.

The opt-in manifest is a regular, singly linked JSON file of at most 4096 bytes,
without selected or ancestor symlinks. Its exact keys are `version`, `services`
and `allocation`. Version is `postgres-harness-cohorts-v1`. Services has exactly
`legacy` and `current`, each an absolute normalized descriptor path. Paths are
distinct. Each descriptor retains every existing single-service validation,
size, identity, readiness, native/configuration hash, permission and original
lease requirement. The original single-service command and validator retain
their meanings; the collection command also accepts this explicitly versioned
manifest in its existing PostgreSQL input position.

Allocation is exactly the ordered three complete records in `base_manifest`.
The entire existing `arboresce-postgres/test/authority_current` harness uses
`current`. Both `arboresce-postgres/test/authority_races` and
`arboresce-postgres/test/qualification` use `legacy`. All other commands retain
the legacy descriptor. List and complete whole-harness execution receive the
same selection. Missing, duplicate, extra, crossed or unknown allocation records
fail before commands launch. No case-level selection, new test target or merged
partial run supplies qualification.

Two complete service observations must describe distinct live cluster system
identifiers, initial PIDs, socket/data directories, protected control roots and
readiness paths. Data/control roots cannot overlap by ancestry. Native tool
path/hash bindings must match across the two services, retaining the existing
exact executable resolver. Both complete file maps and all readiness/descriptors
are independently observed before execution and reopened unchanged afterward.
Manifest bytes and allocation enter the run/context identity. Unknown service
counts and aliases fail; no ambient selector creates an allocation.

Exactly two controllers/clusters may coexist. Each keeps its original finite
lease and at most two physical application connections; harnesses run
sequentially, with at most two such connections active in a selected harness
and an aggregate bound of four across the two namespaces. Controllers,
background server processes and administrative observations retain their
existing separate accounting. The full native/process/profile/resource/input
conservation and both bounded owned cleanup records remain required. Owning and
public-only standalone collections each need their own fresh two-service set.

Each service may perform one terminal restart in its own original namespace.
The current cohort's shared outage occurs only after SQL5 and the complete
literal canonical/shared seed have committed and been independently read.
During actual observed server absence, the real adapter must return Unavailable.
Verified same-cluster successor/adoption and complete unchanged storage/ledger
and canonical authority reads follow before successor-aware finish/cleanup.
All initial-generation shared operations and races precede this restart.
The legacy cohort retains its exact schema2, versions [1,2], useful-record,
outage and fresh-read restart assertions. No reseeding after an outage,
rewritten descriptor, recycled control file, extended lease or suppressed
identity failure establishes either oracle. This is direct isolated harness
qualification; packaged or managed recovery remains a separate requirement.

`cases.json` freezes manifest, ownership separation, exact target routing and
physical-intake/change observations before their consumers. It adds no role,
dependency, source exclusion, coverage exemption or additional reviewer gate.
