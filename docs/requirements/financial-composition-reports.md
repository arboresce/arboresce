# Financial composition report and export contract

This separately versioned target contract preserves existing closed financial, project and lifecycle families. It declares complete report/readback/export selections and their typed boundaries. Shape conformance alone implements no authentication, authority producer, storage, compilation fence, human assurance, worker, delivery or runtime capacity. These actual producers and independently reconstructed literals, source, primary and standalone qualification must pass before enabling support.

## Preservation and explicit profile

Closed financial v1 records, confirmations, manifests, legacy project report/reference/payload shapes, original export JSON/CSV formats and financial/lifecycle operation families retain their exact existing definitions. The qualified six financial-composition operations alone cannot qualify a report or export. A compound event, association or wrapper must never replace the base expense confirmation or upgrade a retained association by implication.

The new profile is `arboresce.project-financial-composition-report-workflows.v1`. It has separate closed request/read/report/payload/export/artifact/operation definitions and a separately registered inventory. It does not widen a closed legacy object with optional fields. Original commands/negative identities/default behavior remain required. No new global CLI command or implicit capability discovery is introduced by this contract.

Three actual owning commands:

- `financial_composition.report.create`: POST `/v1/projects/{project_id}/financial-composition-reports`, with closed common v1 command metadata and body `{project_id,currency,date_policy,period,include_undated}`. Actual project/currency/policy/half-open selection and protected date-policy file remain explicit. The date policy is a typed exact current authorized policy, never an authority assertion.

- `financial_composition.report.export`: POST `/v1/project-financial-composition-reports/{report_id}/exports`, with common command metadata and closed body `{report,expected_control_revision,format}` using the new exact report reference. Scoped agent requirements are project.read and report.read for report creation/read, plus report.export for export, with project_read purpose and exact same-workspace workspace or project grant. Direct human access uses current applicable domain policy and complete owning financial/association/composition/source disclosure. All requirements derive from the canonical subject, with no historical permission shortcut. The new asynchronous profile and exact current availability control are mandatory; an ID-only response qualifies no output.

Owning command-name registration is additive where the owning registry permits it. The legacy closed financial command/operation kinds remain unchanged. New focused plan/resource/stage/cancellation/artifact/content/delivery definitions and their normalized inventory explicitly select this new report subject/profile; existing closed focused export operation definitions must not silently accept a third command or subject. Shared mathematical/clock/encoding algorithms can be reused only through validated separately closed types. Public ordinary use depends on committed owning public bytes and licenses, never this private proposal or another source checkout.

## Exact report identity and selections

`composition_project_report_reference_v1` is closed:
`{kind:"arboresce.project-financial-composition-report-reference.v1",organization_id,domain_id,project_id,report_id,content_sha256}`.

Report ID, report digest, current report availability control, transport receipt, mutable observations and server-side execution data stay outside the preimage. All selected financial controls, confirmations and relationship selection observations stay inside. Current report availability retains its independently observed lifecycle counter and never rewrites the digest.

Every `selected_relationships` row is one closed tagged union:

- Legacy `kind:"legacy_association"`: `{kind,selected,association,observed_association_control_revision,review_event}`. These last four fields retain the exact existing legacy project selection meanings. No materialized composition may be hidden or converted into legacy absence to select this branch.
- Compound `kind:"confirmed_composition"`: `{kind,selected,association,observed_association_control_revision,composition,observed_composition_control_revision,composition_confirmation,compound_review_event}`. `selected` is the unchanged financial manifest selected row, with its exact original expense confirmation. `association` is its exact immutable current binding. `composition` is the full exact immutable composition content/reference; its complete current confirmation and compound wrapper event remain separately retained. `composition` is exactly the existing `financial_composition_content_v1` `{reference,preimage}`; `composition_confirmation` is exactly `financial_composition_confirmation_v1`; `compound_review_event` is exactly `financial_composition_review_event_v1`. The content/control/confirmation fields remain independently joined rather than duplicating a mutable composition snapshot in the digest.

Selected rows correspond one-to-one and in the same canonical expense ordering to `financial_manifest.selected`. Workspace, exact project content, stable expense identity, current expense content/digest, current independently observed financial/association/composition controls and immutable selected identities agree. No historical head, stale project, wrapper-only no-op successor, ambiguous observation or fabricated known absence qualifies selection. A currently proposed or superseded wrapper cannot confer compound relationship approval. Its original base money may remain genuinely confirmed; that fact does not confirm the new project relationship.

For a compound selection, the base selected confirmation must equal the original retained base expense confirmation and its complete financial review history. The compound confirmation independently binds its exact composition/association/project/expense controls and its complete wrapper event. For `confirmed_now`, the canonically retained base financial event and unchanged financial confirmation correspond to the exact globally consumed compound event; for `already_confirmed`, the older base approval/event stays unchanged and distinct from the compound event. The latter must not overwrite expense control, approval, attribution, historical reports or receipts. Retained event expiry alone does not rewrite a committed confirmation; current disclosure and selection eligibility are rechecked.

Legacy selection requires explicit known absence of a post-confirmation composition for that current binding and complete original legacy association-review joins. Missing or unavailable composition collections do not establish absence. A new proposed wrapper cannot fall back to an older association/report or borrow legacy review of an earlier project. Existing standalone legacy reports keep their own contract; this new profile does not retroactively reinterpret them.

`excluded_relationships` carries only exact authorized minimal identity/control/state and deterministic reason. It exposes no inaccessible identity, hidden count, source, policy body, detailed cause or protected content. Each exclusion is a closed tagged union. Legacy `{kind:"legacy_association",identity,observed_association_control_revision,observed_expense_control_revision,revision_state,reason}` retains the existing minimal project association identity object. Compound adds exactly `composition_reference`, `observed_composition_control_revision` and `composition_state` to that closed common exclusion under `kind:"composition"`; the reference is existing financial_composition_reference_v1. Expense and composition states use their owning four-state enums. Reasons are exactly unassigned_date, voided, unresolved, proposed, ineligible, other_currency, composition_proposed and composition_noncurrent. Owning reason order is financial date/state/eligibility first, then permitted selected-currency mismatch, then current wrapper proposed or noncurrent; protected cause detail never appears. Inaccessible expense/relationship metadata is omitted entirely. Unknown required selection observations fail compilation; they do not imply absence, eligibility or a completed enumeration.

The exact projection is computed in this order. First omit wholly inaccessible identities, excluded undated records when include_undated is false, and known dates outside the half-open period; none yields any financial or relationship row/count. Among remaining visible current project relationships, choose the first financial reason in unassigned_date, voided, unresolved, proposed, ineligible. If one exists, emit exactly one unchanged financial exclusion plus exactly one minimal relationship exclusion with that same reason, irrespective of currency or wrapper state; emit no selected row or currency totals contribution. Thus an unresolved USD expense in a CAD report yields financial unresolved and relationship unresolved, never other_currency, even if its wrapper is proposed. The financial exclusion shape has no monetary details or invented base failure. If no financial reason exists, test permitted selected-currency mismatch: mismatch emits only a minimal relationship other_currency exclusion and no financial selected/exclusion row or totals contribution. Only then test the wrapper: an exact current proposed wrapper emits only composition_proposed; an authorized visible noncurrent binding/content/project/control or voided/superseded wrapper emits only composition_noncurrent; another known relationship eligibility failure emits only ineligible. These wrapper-only failures contribute no financial selected/exclusion row or totals. A financially eligible USD expense with a proposed wrapper in a CAD report therefore emits relationship other_currency only. Finally an approved current relationship emits the unchanged financial selected row and its exact tagged relationship selected row, with original financial totals arithmetic. Unknown or stale caller preconditions fail the whole compilation rather than manufacturing an exclusion.

The project-scope adapter considers only exact current relationships for the selected project that the requester may currently know. It does not claim organization-wide completeness, invent a financial failure in the base record, or fall back to legacy approval when a new wrapper exists. The unchanged financial manifest remains a bounded recorded project selection. This ordering is mandatory.

At most 256 selected references and 256 authorized financial exclusions, with the existing at-most-eight currency totals constraints. Each new relationship selection and exclusion array is bounded to 256. Selected entries equal the financial selected count exactly. Relationship exclusions are sorted by stable expense ID, then content version/digest and exact association/composition reference, with no repeated current stable expense/project relationship; selected and excluded stable identities are disjoint. Financial and relationship exclusions can name the same nonselected visible expense, but neither can duplicate it within its own array. An authorized overflow fails the whole compile; no truncation. Empty selection retains declared scope and visible exclusions with empty totals, never invented zero currency entries. The owning project/currency/date selector and exact financial arithmetic, U/L/K incomplete buckets, sign, scale and checked capacity remain authority.
